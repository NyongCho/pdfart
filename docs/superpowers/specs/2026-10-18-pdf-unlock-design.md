# PDF 비밀번호 해제 — 설계·진행 계획 초안

작성: 2026-10-18 · 상태: 사용자 실행 승인, master 배포 직전까지 진행

## 1. 목표와 범위

확정된 요구: 사용자가 **알고 있는 비밀번호를 직접 입력**하면 PDF 암호화를 제거한 사본을 다운로드한다. 기존 병합·추출에 세 번째 기능을 추가한다.

설계 기본값:
- 서버에 PDF·비밀번호를 보내지 않는다. 실행 코드는 앱과 같은 출처에서 제공한다.
- 파일 1개씩 처리하고 원본은 변경하지 않는다. 출력은 `<원본 이름>-unlocked.pdf`로 저장한다.
- PDF를 이미지로 재생성하지 않는다. 텍스트·벡터·문서 구조를 유지하는 엔진을 사용한다.
- 이번 버전에서는 해제 전/후 미리보기, 일괄 처리, 암호 찾기·후보 대입(브루트포스), 암호 설정, 해제 결과의 자동 병합·추출 연계를 제외한다.
- 열기 비밀번호가 있는 PDF를 우선 지원한다. 비밀번호 없이 열리는 권한 제한 문서의 자동 해제는 범위에서 제외한다.
- 전자서명 유효성 보존과 악성 PDF 정화는 제공하지 않는다. 사본 생성 시 서명이 무효화될 수 있음을 안내한다.

사용자가 이 계획과 실패 대응을 승인했다. 이슈 #13 → 독립 worktree → 엔진 검증 → TDD → 리뷰/최종 검증 → dev 병합까지 진행한다. master 병합과 운영 배포는 하지 않고 배포 준비 완료 상태에서 멈춘다.

## 3. 엔진 선택 방향과 선행 통과 조건

### 권장안: qpdf 기반 단일 스레드 WASM + Web Worker

현재 pdf-lib는 암호화 PDF 복호화를 지원하지 않는다. `ignoreEncryption`으로 로드 오류만 무시하는 방식은 사용하지 않는다.

- 브라우저용 qpdf WASM을 별도 Worker에서 실행한다.
- npm 래퍼를 곧바로 채택하지 않는다. 내장 qpdf 및 네이티브 의존성 버전, 소스/빌드 추적성, 라이선스, 알려진 취약점부터 확인한다.
- 유지보수되는 배포물이 기준을 만족하면 최소 래퍼를 사용한다. 그렇지 않으면 검증 가능한 upstream 버전의 재현 빌드가 필요한지 평가한다. 자체 빌드가 일정·운영 범위를 크게 늘리면 구현을 멈추고 선택지를 보고한다.
- 엔진 선택 결과는 정확한 버전/커밋, WASM 해시, 라이선스 고지, 취약점 확인일, 브라우저 실행 증거와 함께 기록한다.

2026-10-18 읽기 전용 후보 조사:
- **통합 1순위 PoC: `@lipoe/browser-qpdf@0.3.1`**. QPDF 12.4.2 라이브러리 API, Vite용 WASM export/locateFile 경로를 제공하고 자체 Worker에서 실행할 수 있다. 바이너리 출처 검증과 비 ASCII 암호 인코딩을 통과해야 채택한다.
- **공급망 우선 대안: `@wasm-zoo/qpdf@0.1.1`의 qpdf-core 산출물**. upstream QPDF 12.4.2, 소스/빌드 pin과 SBOM/provenance를 제공한다. 기본 wrapper를 그대로 채택하는 권고는 아니다.
- 실제 태그 소스에서 기본 wrapper의 `dispose()`는 실행 중 Worker를 종료하지 않고 캐시만 비운다. timeout도 WASM fetch/파일 읽기 이후 시작하며, 공개 adapter에는 document/window 의존성이 있다. **기본 API만으로 즉시 취소·전체 deadline·자체 Worker 실행을 만족한다고 가정하면 안 된다.**
- WASM Zoo 대안은 공개 entry의 `assets` URL로 raw core JS/WASM만 자체 Worker에 적재하는 경로다. `qpdf-core.js` deep import는 exports에 없고, `createQpdfCore`/FS/callMain은 generated glue 내부 계약이므로 공개 API처럼 취급하지 않는다. production Vite/CSP와 유지보수 비용까지 검토한다. 대규모 fork, 취약한 wrapper 복제, 이중 Worker로 우회하지 않는다.
- 순서: lipoe의 provenance/암호 인코딩/기능 검증 → 실패 원인 분류 → 래퍼/배포물 문제라면 raw-core 대안의 동일 게이트와 내부 계약 유지 비용 검토. 공통 qpdf 코어 문제에는 래퍼만 교체하지 않는다. 검증 중 후보가 바뀌면 근거를 이슈에 남긴다.
- 두 패키지 모두 프로젝트에서 실제 실행 검증하지 않았다. upstream의 성공 사례는 우리 앱의 지원 보장이 아니다. MuPDF는 라이선스 선택이 별도 사안이라 기본 대안으로 도입하지 않는다.

대안:
1. 범용 PDF WASM 패키지 전체 도입: 통합은 쉬울 수 있으나 이번 기능 밖의 의존성/번들이 늘어난다. 기본안으로 삼지 않는다.
2. 서버 복호화: 브라우저 한계는 줄지만 파일·암호 미전송 요구와 충돌하므로 제외한다.
3. PDF.js 렌더링 후 이미지 PDF 생성: 검색 가능한 텍스트·양식·링크 등을 잃으므로 제외한다.

**엔진 검증 통과 전 제품 코드에 의존성을 추가하지 않는다.** 승인된 작업 범위의 격리된 실험에서 다음을 증명한다.

- 실제 production build에서 같은 출처의 Worker/WASM 자산이 로드되고, 별도 서버 처리 없이 복호화된다.
- COOP/COEP나 SharedArrayBuffer가 없어도 동작하는 빌드를 우선한다. 배포 헤더 변경이 필요하면 영향 검토 없이 진행하지 않는다.
- AES-128, AES-256의 일반적인 PDF 암호화 fixture가 올바른 암호로 열리고 암호 없는 결과로 저장된다. 세부 revision별 지원 표를 남긴다.
- RC4 입력은 지원 여부를 따로 검증하고 명시한다. 기존 취약 알고리즘 읽기와 새 암호화 생성은 구분한다.
- 공백·특수문자·한글 비밀번호를 엔진의 문서화된 인코딩 규칙에 따라 처리한다. 앱이 임의로 trim/정규화/추측하지 않는다.
- 경고 반환, 손상 문서, 지원하지 않는 보안 처리기, 잘못된 암호를 구분할 수 있다. 경고/부분 성공은 첫 버전에서 다운로드 성공으로 처리하지 않는다.
- 일반 qpdf 종료 코드만으로 암호 오류와 손상을 구분할 수 있다고 가정하지 않는다. 선택한 고정 버전에서 오류 분류를 실제 fixture로 입증하고, 불명확한 오류는 안전한 일반 처리 실패로 표시한다.
- native `--check`/`--linearize` 같은 불필요한 진단·재배열 경로를 제품의 unlock 작업에 추가하지 않는다. 출력 검증용 독립 판독은 테스트에서 수행한다.
- 실제 엔진을 사용한 fixture 테스트를 기존 CI에서 반복 실행할 수 있다. mock만 통과한 상태는 채택 근거가 아니다.

### 3.1. 검증 실패 시 분기와 재시도 한도

실패하면 먼저 합성 fixture, 정확한 입력 암호, 기대 결과, 패키지/엔진 버전, 실패 단계와 최소 재현을 남긴다. 사용자 파일·암호는 이슈에 첨부하지 않는다. fixture/테스트 자체 오류인지 독립 판독기로 확인한다. 틀린 암호·손상 파일을 의도대로 거절한 것은 검증 실패가 아니라 정상 통과다.

| 실패 원인 | 다음 조치 | 통과/전환 기준 |
| --- | --- | --- |
| Vite 자산 경로, WASM MIME, Worker 시작, 앱 상태/취소 연결 등 통합 문제 | 실패 회귀 테스트를 고정하고 해당 연결만 수정 | production build에서 동일 재현과 관련 회귀 통과. 메인 스레드 처리나 CSP 무차별 완화로 우회하지 않음. |
| 래퍼의 비밀번호 인코딩/오류 분류/수명 문제 | 문서화된 API 범위의 얇은 adapter로 해결 가능한지 확인. 불가능하면 raw-core 대안 검증 | 공백·한글 포함 암호와 취소/전체 deadline을 유지. 암호 변형, 테스트 삭제, 큰 fork로 통과시키지 않음. |
| 바이너리 출처 불명, 라이선스 부적합, 관련 미해결 취약점 | 해당 배포물 채택 중단. 추적 가능한 다른 배포물 또는 수정된 upstream의 재현 빌드 필요성 평가 | 출처/고지/보안 게이트를 그대로 통과해야 함. npm audit 경고 억제·force 설치로 진행하지 않음. |
| 유효한 문서에서 내용 손실/복호화 실패 | 같은 버전의 native qpdf와 독립 PDF 판독기로 WASM/래퍼 문제인지 공통 코어 문제인지 구분 | 두 후보 모두 qpdf 계열이라 공통 코어 결함이면 래퍼 교체만으로 해결했다고 판단하지 않음. 수정 upstream 확인 또는 다른 엔진의 별도 평가로 전환. |
| 큰 파일/특정 브라우저에서만 시간·메모리 초과 | 불필요한 복사/객체 보유를 줄인 뒤 재측정. 남는 한계는 파일 크기·지원 브라우저 제한안으로 제시 | 암호 기능/내용 보존/취소는 필수 유지. 기존 제안 범위 축소는 근거와 사용자 확인 없이 조용히 반영하지 않음. |

재시도 정책:
- 동일 원인에는 **최초 재현 후 최대 2회의 근거 있는 수정·재검증**만 수행한다. 새 가설/증거 없이 같은 명령을 반복하지 않는다.
- 후보 1개당 최대 1업무일의 검증 시간 상한을 두고, 2개 후보까지만 기존 범위에서 평가한다. 횟수/시간 중 먼저 도달한 한도를 적용한다. 이는 완료 시간 보장이 아니라 무한 조사 방지 한도다.
- 보안·라이선스·비밀정보 노출·내용 손실은 횟수가 남아 있어도 현재 산출물의 채택/병합을 즉시 보류한다. 범위를 좁힌 수정이나 교체가 새 증거로 안전성을 입증해야 재개한다.
- 두 후보가 실패하거나 공통 코어 결함이면, 이슈에 결과 표와 함께 **(A) 별도 이슈의 자체 WASM 빌드/수정 upstream 검증, (B) 다른 엔진의 라이선스·유지보수 검토, (C) 기능 보류**를 제안한다. 자체 빌드만으로 공통 코어 버그가 고쳐진다고 가정하지 않는다. 추가 일정·의존성·범위는 사용자 선택 전에 실행하지 않는다.
- 어떤 분기에서도 서버 업로드, 래스터화로 내용 손실, 비밀번호 후보 대입, 실패한 출력을 다운로드하는 우회는 하지 않는다. 통과한 후보가 없으면 feature PR을 dev/master에 병합하지 않고 기존 병합·추출은 그대로 둔다.

## 4. 사용자 흐름과 오류 정책

1. `비밀번호 해제` 탭 선택.
2. PDF 1개 선택/드롭. 파일명·크기와 로컬 처리 안내 표시.
3. 마스킹된 비밀번호 입력, 표시/숨기기 토글 제공. 빈 입력은 실행하지 않는다. 공백만으로 이루어진 비밀번호도 임의로 잘라내지 않는다.
4. `비밀번호 해제 다운로드` 실행. 중복 실행을 막고 로딩/처리 상태와 취소 버튼 제공.
5. 성공한 경우에만 암호 없는 사본 다운로드. 실패한 경우에는 오류와 재시도 방법 표시.

오류 구분: 비밀번호 불일치 / 암호화되지 않은 PDF / 손상되거나 PDF가 아닌 파일 / 미지원 암호화 / 크기 초과 / 엔진 로드 실패 / 처리 실패 / 시간 초과.

- 암호화되지 않은 입력에는 `이미 비밀번호가 없는 PDF`를 표시하고 중복 사본을 만들지 않는다.
- 입력 MIME만으로 PDF 여부를 판정하지 않는다. 파일 선택 힌트와 실제 엔진 파싱 결과를 구분한다.
- 일반 오류 메시지는 한국어 코드 매핑으로 만든다. 엔진의 원문 stdout/stderr, 암호가 포함될 수 있는 인수나 예외를 DOM/console/리포트에 그대로 노출하지 않는다.
- 탭 이동·파일 교체·취소 시 이전 작업은 종료되고 늦게 도착한 결과/오류/다운로드는 폐기한다.
- 암호 상태는 처리 완료(실패 포함), 취소, 파일 교체, 탭 이동 시 비운다. 재시도에는 다시 입력한다.
- 저장소(localStorage/IndexedDB 등), URL, 분석 이벤트에 파일·비밀번호를 남기지 않는다. JavaScript/브라우저 메모리의 물리적 완전 삭제까지 보장한다고 표현하지 않는다.
- 비밀번호 입력은 `type="password"`, `autoComplete="off"`, `spellCheck={false}`를 기본으로 한다. 자동완성 차단은 브라우저에 대한 힌트이며 비밀번호 관리자/확장 기능의 저장까지 앱이 통제한다고 약속하지 않는다.
- 초안의 보호 한도는 **파일 50 MiB, 엔진 로드 포함 작업 60초, 동시 작업 1개**다. PoC에서 기본 지원 환경에 부적절하면 변경 이유와 검증 결과를 계획에 반영한 뒤 진행한다. 대용량 문서의 메모리 사용량을 파일 크기만으로 보장하지 않는다.

제안 계약:

```text
unlockPdf(file: File, password: string,
          options?: { signal?: AbortSignal, timeoutMs?: number }): Promise<Uint8Array>

Worker 요청: { id, type: 'unlock', input: ArrayBuffer, password }
Worker 응답: { id, type: 'success', output: ArrayBuffer }
          | { id, type: 'error', code }
```

작업 ID가 일치하는 응답만 수용한다. 암호는 성공/오류 메시지에 되돌려 보내지 않는다. 성공·실패·취소·기한 만료 모두 타이머·리스너·Worker를 정리한다. Worker 미지원이면 명시적인 안내로 끝내고 UI 스레드/서버 처리로 자동 우회하지 않는다.

전체 60초 기한과 AbortController는 UI 실행 시작 시 설정해 facade 동적 import·파일 읽기·엔진 로드까지 포함한다. 지연 import가 취소 뒤에 완료돼도 Worker를 만들지 않는다. facade 단독 호출의 timeout은 같은 취소/정리 경로를 사용한다. 다운로드 직전에도 현재 작업 ID와 취소 여부를 확인한다.

## 6. TDD 진행 순서

모든 구현 단계는 **실패 테스트 → 실패 이유 확인 → 최소 구현 → 통과 확인 → 자체 리뷰 → 결정 근거가 포함된 커밋** 순서로 진행한다.

### A. 이슈와 실행 기준 확정
- [ ] 기능 이슈에 범위·제외 사항·엔진 검증 조건·테스트 표 등록.
- [ ] 원격 `dev/master`와 열린 PR을 다시 확인. 승인된 `dev`에서 독립 worktree와 `feat/<이슈번호>-pdf-unlock` 브랜치 생성.
- [ ] 계획 검토 및 필요한 새 의존성 도입 범위를 승인받은 후 아래 실험 시작.

### B. 엔진 검증과 fixture 확보 — 구현 전 중단 가능한 단계
- [ ] 최소 후보의 버전·라이선스·빌드 추적·취약점 보고서 작성. npm audit만으로 WASM 내장 C/C++ 라이브러리 안전성을 판정하지 않음.
- [ ] 자체 생성된 원본과 암호화 fixtures 준비. 생성기와 검증기는 역할을 분리하고, 결과를 다른 PDF 판독기로 읽어 엔진 자기 검증만 남지 않도록 함.
- [ ] 기존 pdf-lib를 기본 설정으로 사용해 출력의 비암호화·페이지/회전·폼·메타데이터를 확인한다. 기존 PDF.js는 동일 브라우저에서 비암호화 원본과 결과의 텍스트·렌더·outline/annotation/attachment를 비교하는 oracle로 사용한다. 제품 unlock 흐름에는 이 검증용 두 엔진을 로드하지 않는다. 확인할 요소별 expected 값을 fixture manifest에 기록한다.
- [ ] 생산 빌드에서 알려진 암호 성공/틀린 암호 실패를 실제 실행. 출력에 암호가 없고 주요 문서 요소가 보존되는지 검사.
- [ ] 자산 크기, 첫 로드/반복 실행 시간, 취소, 대용량 대표 샘플을 기록. 기존 560회 측정 결과를 이번 기능의 성능 증거로 재사용하지 않음.
- [ ] 비밀번호 없이 열리는 권한 제한 문서/비암호화 문서와 열기 암호가 있는 문서를 구별하는 API 또는 검사 경로를 입증. 빈 사용자 암호로 자동 해제하는 동작은 연결하지 않음.
- [ ] 통과 시 후보와 버전을 고정. 통과하지 못하면 UI를 먼저 만들지 않고 근거와 대안 보고.

## 8. worktree·에이전트·GitHub 기록

- 기본 구성: **구현 executor 1명 + 독립 code-reviewer 1명 + 메인 orchestrator**. 밀접하게 연결된 UI/Worker를 억지로 병렬 구현하지 않는다.
- 엔진 후보/라이선스 검토는 dependency-expert가 별도 읽기 전용 작업으로 지원 가능. 실행자는 지정된 feature worktree만 수정하고 다른 작업자의 변경을 되돌리지 않는다.
- 기본은 기능 이슈 1개와 `dev` 대상 PR 1개. 자체 qpdf 빌드 체계가 필요해 독립적인 큰 변경이 되면 먼저 별도 이슈/PR로 분리하고 기존 순차 병합 규칙 적용.
- 실행자가 자체 리뷰·RED/GREEN·실제 엔진 증거를 PR 본문/댓글에 기록한다. 메인 orchestrator가 코드 리뷰와 수정 요청을 GitHub 댓글로 남긴다.
- 수정자는 해당 댓글에 변경 커밋·재검증 결과로 답한다. 같은 GitHub 계정의 에이전트 댓글을 독립 인간 승인으로 표현하지 않는다.
- 선행 PR 병합/원격 변경이 있으면 최신 `dev`를 fetch해 충돌과 논리 회귀를 해결한 뒤 다시 테스트한다.
- 최종 head SHA의 CI·리뷰·검증이 모두 확인된 경우에만 orchestrator가 병합한다. 강제 push/관리자 우회로 실패한 게이트를 넘지 않는다.
- PR/이슈/댓글은 간결한 한국어. 커밋은 intent와 필요한 Lore trailers로 결정 근거를 남긴다.

## 9. 위험과 중단 조건

- **엔진 공급망**: npm 버전이 새로워도 내장 qpdf가 오래됐을 수 있음 → upstream/네이티브 종속성 버전·출처·해시 검증. 관련 미해결 취약점이나 추적 불가 바이너리는 채택하지 않음.
- **문서 손실**: 단순히 열리는 PDF가 나와도 양식/링크 등이 손실될 수 있음 → 요소별 fixture와 독립 판독. 이미지 재생성 우회 금지.
- **무한 대기/메모리**: WASM 동기 작업은 AbortSignal만으로 취소되지 않음 → 독립 Worker terminate + 전체 작업 deadline + 크기 제한. 지원 한도 검증 전 무제한 파일 약속 금지.
- **민감 정보 노출**: stdout/stderr/예외에 암호가 포함될 가능성 → 원문 비노출, 고정 오류 코드, 요청/로그/저장소 검증.
- **범위 확대**: 암호 찾기, 서버 처리, 인증서 기반 복호화, 상용/강한 copyleft 의존성, 배포 헤더 변경이 필요하면 자동 채택하지 않고 별도 결정.

완료 기준: 선택 엔진 근거, 위 검증 결과, 한국어 자체/메인 리뷰 기록, 최종 CI가 있고 `dev` PR 병합까지 확인된 상태. 최종 dev 검증 후 master 배포 준비 완료 상태에서 멈춘다.

## 12. 실행 중 엔진 게이트 결정 (2026-10-18)

- 후보1은 배포물 추적/고지 결함으로 보류했다. 후보2 `@wasm-zoo/qpdf@0.1.1` raw core를 제품 TDD 대상으로 선택한다. 공식 wrapper는 사용하지 않는다.
- 실제 production Vite/Chrome와 독립 pdf-lib/PDF.js에서 AES128, AES256 R5/R6, RC4 40/128, 한글·양끝 공백, 잘못된 암호, 비암호화/owner-only 구분, warning 출력 거절, 내용 보존, 취소 후 재시도가 검증됐다. 이는 feasibility이며 제품 전체 합격은 아니다.
- 제품 경로는 `--stream-data=preserve --decode-level=none`를 강제한다. 이 옵션으로도 전체 fixture가 다시 통과했다. 검사/linearize/image-optimization 경로는 실행하지 않는다.
- native qpdf의 자원 소모 이슈를 무조건 안전하다고 간주하지 않는다. 선택 WASM은 자체 linear memory 최대 512 MiB, 초기 32 MiB로 빌드됐으며 호출자가 더 낮은 memory를 주입할 수 없다. 50 MiB/60초/Worker 제한은 JS/MEMFS/브라우저 전체 RAM 상한이나 악성 PDF 안전 보장이 아니다. 저메모리 환경 제약을 명시하고 자원 제한·취소 테스트와 잔여 위험 기록을 출시 조건으로 둔다.
- 공급망 조건: exact npm SRI와 core JS/WASM SHA256 고정 검증, 원문 고지 배포, SBOM의 libjpeg 9f 정정 기록, source-to-WASM 독립 재빌드 미검증 명시, 비공개 generated-glue 계약/업그레이드 재검증.
- zlib gz* write API 관련 공개 CVE는 확인한 qpdf source에 호출 경로가 식별되지 않았다. 취약점 없음으로 표기하지 않고 예외 근거와 갱신 조건을 기록한다.
- 독립 architecture gate는 제품 TDD 착수 허용/WATCH. 최종 리뷰에서 위 조건과 실제 제품 증거를 확인하기 전 dev 병합하지 않는다. master/운영 배포는 계속 금지다.
